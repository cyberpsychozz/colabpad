Жёсткая верификация MVP: что отсекаем
Каждый пункт сверен с блоком 4.2 бизнес-гипотезы. В MVP не входит то, что не закрывает главную боль «негде быстро порисовать вместе, и Undo мешает заканчивать»:
Отсекаем
Почему
Регистрация, аккаунты, личный кабинет
Противоречит «вход за 10 секунд». Доступ даёт сама ссылка.
Три типа холстов (личный / по приглашению / открытый)
В MVP один тип: холст по ссылке. «Личный» = не делиться ссылкой, «по приглашению» = отправить ссылку нужным людям.
Ссылка только для просмотра, пароль на холст
Риск порчи чужими принят для MVP (ссылка случайная). Первое улучшение после MVP.
Открытые общие холсты, модерация, подписки
Требуют аккаунтов и модерации. Вне MVP.
Ластик, слои, доп. кисти
Ластик противоречит ядру продукта. Слои и кисти не нужны для проверки гипотезы.
Режим «Practice» с Undo (запасной вариант из блока 9.3)
Исключён окончательно — не только из MVP, но и из запасных вариантов. Отмена в любом виде противоречит ядру продукта. Риск оттока проверяем замером Retention D1/D7, а не откатом механики.
Экспорт таймлапса в видео, оплата
Pro-функции. Интерес проверяем fake-door кнопкой (FR-9).
Мобильное приложение, Telegram Mini App
Веб работает на всех устройствах.

1.2. Анализ ограничений и границ
Внешние ограничения
Хостинг. Платный хостинг 250 ₽/мес с постоянным диском: SQLite-файл не теряется при перезапуске и передеплое, сервер не засыпает. Домен — 120 ₽. Итого ≈ 250 ₽/мес + 120 ₽ за домен — в рамках бюджета из блока 8. Путь к БД задаётся через DB_PATH.

Вычисления. Вся отрисовка, таймлапс и PNG — в браузере. Сервер только пересылает и сохраняет штрихи.
Команда. Один разработчик, 7 дней. Стек выбран под это: FastAPI на сервере (Pydantic даёт валидацию и документацию API автоматически), чистый JavaScript на клиенте без фреймворков.

2. Проектирование архитектуры
Принцип: минимально, но достаточно. Монолит из одного процесса Python (FastAPI + Uvicorn), одного файла БД и одной веб-страницы.
2.1. Компонентный состав
Слой
Решение
Почему
Клиент
Веб-приложение: HTML5 Canvas + Vanilla JS (Vite для сборки). Pointer Events для мыши, тача и стилуса.
Работает везде без установки, быстрее всего прототипировать. React не нужен: экранов три.
Сервер
Python 3.12 + FastAPI (REST и раздача статики через StaticFiles) + python-socketio (ASGI-приложение, смонтированное в FastAPI) для реального времени. Uvicorn, строго 1 воркер. Валидация — модели Pydantic v2, настройки — pydantic-settings.
Socket.IO даёт комнаты, ack и автопереподключение клиента из коробки. Один воркер: комнаты и онлайн-список живут в памяти процесса, а порядок seq гарантируется без блокировок.
Связь
REST (FastAPI) — создание и загрузка холста. WebSocket (Socket.IO-протокол, клиент socket.io-client, сервер python-socketio) — штрихи и присутствие.
REST проще кешировать и отлаживать. WS — для событий с низкой задержкой.
Хранилище
SQLite через стандартный модуль sqlite3, режим WAL. Две таблицы + счётчики. Без ORM: 6–7 SQL-запросов в модуле repo.py.
Реляционная схема проста (холст 1→N штрихов). Транзакция выполняется синхронно, без await внутри, поэтому в одном event loop две вставки не перемешаются.
Вычисления
Только в браузере: сглаживание, упрощение линии, таймлапс, PNG.
Сервер остаётся лёгким, хостинга за 250 ₽/мес хватает с запасом.
Деплой
Хостинг 250 ₽/мес: Uvicorn (1 воркер) под systemd за Nginx (прокси с поддержкой WebSocket) + постоянный диск для collabpad.db. Свой домен (120 ₽), HTTPS-сертификат Let’s Encrypt.
Данные переживают передеплой, нет холодного старта. См. 1.2.

2.2. Архитектурная схема

Рис. 1. Компоненты системы и потоки данных
Сценарий A. Создание холста
Пользователь нажимает «Создать холст» на главной.
Клиент отправляет POST /api/canvases.
Сервер генерирует id (nanoid, 10 символов), сохраняет CANVAS с размерами из конфига.
Сервер возвращает 201 {id, url}. Клиент переходит на /c/{id}.
Сценарий B. Открытие холста по ссылке
Браузер открывает /c/{id}. FastAPI отдаёт index.html (фронтенд собран Vite в static/).
Клиент делает GET /api/canvases/{id}. Валидация: формат id; холст существует, иначе 404.
Сервер возвращает параметры холста и все штрихи по возрастанию seq. Клиент рисует их и запоминает lastSeq.
Клиент подключается к Socket.IO и отправляет canvas:join {canvasId, name}. Сервер добавляет сокет в комнату и рассылает presence:update.
Если между шагами 3 и 4 кто-то успел нарисовать, клиент догружает GET /api/canvases/{id}/strokes?afterSeq={lastSeq}.
Сценарий C. Рисование штриха
pointerdown → pointermove: клиент собирает точки [x, y, pressure] и сразу рисует их локально.
pointerup: трансформация — упрощение линии (Ramer–Douglas–Peucker, ε = 0.5 px), округление до 0.1 px. Штрих получает clientId (UUID) и кладётся в очередь отправки.
Клиент шлёт stroke:add с ack-колбэком.
Сервер: валидация (схема, лимиты, rate limit) → в одной транзакции seq = stroke_count + 1, сохранение STROKE, инкремент stroke_count.
Сервер отвечает автору {ok: true, seq} и рассылает stroke:new остальным в комнате.
Получатели рисуют штрих на своём холсте. Автор удаляет штрих из очереди отправки.
Сценарий D. Таймлапс и PNG
Таймлапс: клиент очищает отдельный слой-canvas и проигрывает уже загруженные штрихи по seq. Запросов к серверу нет.
PNG: canvas.toBlob("image/png") основного холста → скачивание collabpad-{id}.png. Запросов к серверу нет.

Рис. 2. Сущности и связи
Правила целостности
Уникальные ключи: canvas.id; пара (canvas_id, seq) задаёт порядок штрихов; пара (canvas_id, client_id) не даёт сохранить один и тот же штрих дважды при переподключении.
Обязательные поля: все, кроме stroke.author_name.
Неизменяемость: штрихи нельзя изменить или удалить — это гарантируют и код (нет таких методов), и триггеры БД. Меняется только счётчик canvas.stroke_count.
Ссылочная целостность: PRAGMA foreign_keys = ON; штрих без существующего холста не сохранится.

Граничные случаи
Обрыв связи во время рисования. Штрихи копятся в очереди отправки (в памяти вкладки). После переподключения клиент делает canvas:join, догружает штрихи afterSeq=lastSeq, затем отправляет очередь. Повторная отправка безопасна благодаря UNIQUE(canvas_id, client_id): сервер вернёт уже назначенный seq.
Два человека рисуют одновременно. Порядок определяет seq, назначенный сервером. Во время сессии локальный штрих может лежать «поверх» чужого не в том порядке — для MVP это допустимо; после перезагрузки порядок всегда по seq.
Закрыли вкладку, не дождавшись ack. Неотправленные штрихи теряются. Индикатор «Сохранение…» предупреждает об этом.
Сервер перезапустился. Socket.IO переподключается сам; данные в SQLite на постоянном диске не теряются.
Холст заполнен во время рисования. Последний штрих получает CANVAS_FULL и исчезает у автора; всем приходит canvas:full.
3.2. Алгоритмические процессы
Подготовка штриха (клиент)
Сбор точек: pointermove с getCoalescedEvents(); координаты экрана переводятся в логические координаты холста 1600×1000.
Давление: event.pressure; если устройство его не даёт (мышь отдаёт 0 или 0.5), используем 0.5.
Отбрасываем точки ближе 1 px к предыдущей.
На pointerup — упрощение RDP с ε = 0.5 px, округление до 0.1 px.
Если точек больше 2 000 — делим на несколько штрихов (с перекрытием в 1 точку).
Отрисовка (одинаково для live, загрузки и таймлапса)
Линии соединяются квадратичными кривыми через середины отрезков; lineCap и lineJoin = round.
Толщина сегмента = width × (0.5 + pressure); для мыши это ровно width.
Холст рендерится с учётом devicePixelRatio, чтобы линии были чёткими на Retina.
Обработка на сервере
Проверка схемы и лимитов (см. 1.2) моделью Pydantic StrokeIn — до обращения к БД. Ошибки Pydantic переводятся в VALIDATION_ERROR с полем field.
Транзакция: проверить stroke_count < MAX_STROKES → если client_id уже есть, вернуть его seq → иначе INSERT с seq = stroke_count + 1 и инкремент счётчика.
Рассылка stroke:new в комнату, кроме отправителя.
Таймлапс
Длительность на скорости 1×: 40 мс на штрих, но не больше 60 с всего (если штрихов много, время на штрих уменьшается).
Скорости 1×, 2×, 5×; пауза; ползунок перемотки по номеру штриха.
Штрих появляется целиком (без анимации внутри штриха) — проще и быстрее.
Конфигурация
Все параметры — в app/config.py (класс Settings на pydantic-settings) с переопределением через переменные окружения (.env). Клиент получает нужные значения в ответе GET /api/canvases/:id.

5.2. Проверка качества
Вопрос
Ответ
ТЗ покрывает все 3 функции MVP?
Да. Core №1 — FR-3, 4, 5; Core №2 — FR-1, 2, 6; Core №3 — FR-7, 8. Плюс FR-9 для проверки монетизации.
Нет ли избыточности?
Нет аккаунтов, типов доступа, модерации, очередей, кешей и внешних сервисов. Один процесс и один файл БД.
Понятны ли граничные случаи?
Да: обрыв связи, дубли, одновременное рисование, лимиты, заполненный холст, перезапуск сервера (3.1).
План реалистичен?
50 ч на 7 дней при ~7 ч/день. Есть запас в T14 и «отрезаемый» T9.

5.4. Открытые вопросы
Монетизация «платный штрих» (по модели The Million Dollar Homepage)
Референс. The Million Dollar Homepage (Алекс Тью, 2005): страница 1000×1000 пикселей, каждый пиксель продавался за $1 блоками 10×10. Все пиксели были распроданы за несколько месяцев. Ценность создавали дефицит и необратимость: купленное место навсегда.
Идея для CollabPad. На большом публичном холсте каждый штрих платный (например, 10–50 ₽). Механика «без отмены» здесь работает сильнее: заплатил — штрих остаётся навсегда, стереть его не может никто. Это может стать главным холстом проекта и инфоповодом для соцсетей.
Что нужно обсудить:
Вопрос
Комментарий
Где это работает?
Только на открытом публичном холсте (тип 3 из исходной идеи). Личные холсты по ссылке остаются бесплатными, иначе ломается «вход за 10 секунд».
Чем платить: штрих, длина или площадь?
Цена за штрих проще, но один штрих может закрасить полхолста. Варианты: ограничить длину и толщину платного штриха или брать плату за «чернила» (длину линии).
Конфликт с Freemium
В блоке 7 модель — подписка Pro за 199 ₽/мес. Нужно решить: «платный штрих» вместо Pro, вместе с ним или только как разовый спецпроект.
Модерация
Платный штрих нельзя стереть, а оплатить его может кто угодно. Нужны правила и право удалять запрещённый контент — это прямо противоречит неизменяемости (NFR-4) и требует отдельного решения.
Юридическая сторона
Приём платежей: ИП или самозанятость, онлайн-касса и чеки (54-ФЗ), договор-оферта, возвраты.

Влияние на архитектуру (если решим делать): платёжный провайдер (например, ЮKassa) и вебхук подтверждения оплаты; у штриха появляется статус «ожидает оплаты» → «оплачен», и на холст попадают только оплаченные; нужна идентификация покупателя (хотя бы email для чека). Это ≈ 2–3 дня работы — в 7-дневный MVP не входит.
Как проверить дёшево сейчас: тем же fake-door, что и Pro (FR-9) — кнопка «Купить штрих на большом холсте» с окном «Скоро» и счётчиком metric.stroke_buy_click. Это +30 минут к задаче T12 и даёт данные для решения до начала разработки.
